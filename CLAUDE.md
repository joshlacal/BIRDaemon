# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**BIRDaemon** (`bird-daemon`) is a Bluesky DM chatbot daemon written in Rust. It logs into a Bluesky account, joins MLS-encrypted chat conversations (the same `blue.catbird.mlsChat` stack used by Catbird iOS and catmos), decrypts incoming messages, forwards them to an LLM/agent backend, and sends the encrypted reply back into the conversation.

It is **not** a workspace — it's a single binary crate that depends on `catbird-mls` and `catbird-atproto` via path dependencies.

## Build & Run

```bash
cd BIRDaemon
cargo build            # debug
cargo build --release  # release binary -> target/release/bird-daemon
cargo check
cargo fmt && cargo clippy --all-targets

# Run (reads config from ~/Library/Application Support/BirdDaemon/, see below)
RUST_LOG=info cargo run
```

There is no README, deploy script, or systemd unit in the repo. Runtime data lives under `~/Library/Application Support/BirdDaemon/`.

## Environment Variables

Only two true env vars; everything else is in `config.json` (see below).

| Var | Where | Purpose |
|-----|-------|---------|
| `BIRD_APP_PASSWORD` | `~/Library/Application Support/BirdDaemon/.env` (loaded via `dotenvy`) | Bluesky **app password**. Required. Also used as the SQLCipher encryption key for the MLS DB. |
| `RUST_LOG` | process env | `tracing` `EnvFilter`; defaults to `info` if unset. |

There is no `.env.example`. The `.env` file must contain `BIRD_APP_PASSWORD=...`.

## Configuration (`config.json`)

Loaded from `~/Library/Application Support/BirdDaemon/config.json` (`src/config.rs`, `BirdConfig`). **All fields are required** — they are non-`Option` with no `#[serde(default)]`, so a missing key makes `load_config()` fail at startup. Keys are camelCase:

```json
{
  "handle": "bot.bsky.social",
  "llmBackend": "...",
  "llmBaseURL": "https://...",
  "llmApiKey": "...",
  "llmModel": "...",
  "systemPrompt": "...",
  "acceptChatRequests": true,
  "replyToAllMessages": true,
  "maxReplyCharacters": 1000
}
```

Note: `llmBaseURL` / `llmApiKey` / `llmModel` are still required in the JSON, but the **active reply path ignores them** (see Data Flow). They feed the dormant `LlmClient` in `src/llm.rs`, not the wired-up `BridgeClient`.

Runtime files created alongside `config.json`: `keychain.json`, `credentials.json`, `bird.db` (app storage), and `mls-state/<sanitized-did>.db` (encrypted MLS/OpenMLS state).

## Architecture / Data Flow

Entry point: `src/main.rs`.

1. **Auth** — Authenticates to Bluesky via `jacquard` `MemoryCredentialSession` using the **legacy app password** (not OAuth). Resolves DID + PDS endpoint.
2. **API client** (`src/xrpc_client.rs`, `BirdApiClient`) — Implements `catbird_mls::orchestrator::MLSAPIClient`. Routes all MLS XRPC calls through the PDS using the `atproto-proxy` header (`did:web:mlschat.catbird.blue#atproto_mls`). Handles token refresh / re-auth via the jacquard session.
3. **MLS context + orchestrator** — `MLSContext::new(...)` opens the per-DID SQLCipher DB (encrypted with the app password). `MLSOrchestrator` is wired with local impls: `SqliteStorage` (`storage.rs`), `FileCredentialStore` (`credentials.rs`), `FileKeychain` (`keychain.rs`). Startup then: `initialize(did)` → `ensure_device_registered()` → publish `blue.catbird.mlsChat.device` record to the ATProto repo (so other clients accept our key packages) → `replenish_if_needed()` (publish key packages).
4. **Event loop** (`src/bot.rs`, `BirdBot::run`) — Subscribes to MLS events over a DAG-CBOR WebSocket (`src/websocket.rs`, ticket obtained via the PDS proxy). On each `Message` event it decrypts via `orchestrator.process_incoming`, on `GroupReset` it records RESET_PENDING (persist-only). A 30s timer drives `sync_with_server` and deferred rejoin.
5. **LLM reply** — The **live** path is the **bridge** (`src/bridge_client.rs`, `BridgeClient`): `main.rs` constructs `BridgeClient::new("http://127.0.0.1:8789")`. Decrypted plaintext is POSTed to the `mls-chat-channel` bridge (`/message`), then it polls `/reply/:conversation_id` for the response generated by Claude Code. The reply is sent back via `orchestrator.send_message`.
   - `src/llm.rs` (`LlmClient`, an OpenClaw / OpenAI-compatible chat-completions gateway using `llmBaseURL`/`llmApiKey`/`llmModel`) is the **alternate, currently-unwired** LLM backend. It is not constructed in `main.rs`. Don't describe it as the active path.

## Key Dependencies

- **`catbird_mls` (`../catbird-mls`, path dep)** — MLS protocol + orchestrator (OpenMLS, recovery policy, sync). BIRDaemon implements the orchestrator's `MLSAPIClient` / `MLSStorageBackend` / `CredentialStore` / `KeychainAccess` traits and consumes its types (`ConversationState`, `IncomingEnvelope`, etc.) **directly**. Built with `default-features = false`.
- **`catbird-atproto` (`../catbird-atproto`, path dep)** — Generated AT Protocol types with correct `$bytes` serialization.
- **`jacquard` 0.9** (+ `jacquard-common`, `jacquard-identity`) — ATProto client: auth, identity resolution, session/token lifecycle.
- **`[patch.crates-io] jacquard-oauth`** points at `../nest/patches/jacquard-oauth` — Catbird's fork that adds the `transition:chat.bsky` scope.
- `rusqlite` with `bundled-sqlcipher`, `tokio-tungstenite` (WebSocket), `ciborium` (DAG-CBOR frames), `reqwest` (rustls).

## Gotchas

- **Build breaks on `catbird-mls` evolution.** Because BIRDaemon matches on / constructs upstream orchestrator types directly, adding an enum variant or struct field in `catbird-mls` breaks compilation here (the workspace "Jacquard struct-evolution breaks consumers" pattern). As of 2026-05-31 this is failing on a new `Quarantined` `ConversationState` variant — fix by adding the arm in `src/storage.rs`.
- **CMake 4.x / `audiopus_sys` (workspace backlog N2):** `catbird-mls` transitively pulls in `audiopus_sys`, which fails under CMake 4.x. **This crate already handles it** — `.cargo/config.toml` sets `CMAKE_POLICY_VERSION_MINIMUM = "3.5"`, so no manual export is needed when building from this directory. (Unlike sibling crates, where you must export it yourself.)
- **The bridge must be running.** The live reply path requires the `mls-chat-channel` bridge listening on `http://127.0.0.1:8789`. If it's down, replies fail (the daemon logs the error but sends nothing).
- **App password is dual-purpose:** it authenticates Bluesky *and* serves as the SQLCipher key for the MLS DB. Changing it orphans the existing encrypted state.
- **Never inline External Commits.** The bot intentionally avoids proactive/inline rejoins — it flags `NEEDS_REJOIN` and lets the 30s sync loop drive recovery. This is deliberate epoch-inflation discipline; preserve it (`record_group_reset` is persist-only, recovery is deferred/reactive).
- **Device-limit cleanup is aggressive.** If `ensure_device_registered()` hits the device limit, the startup handler in `main.rs` removes **all** previously registered devices to make room before retrying. Be aware when running multiple instances for the same account.
- **Messages beyond the epoch retention window are dropped.** `MAX_PAST_EPOCHS = 5`; messages from epochs older than `local_epoch - 5` are discarded rather than recovered.
